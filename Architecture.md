# kubewing architecture

How kubewing is built and why. For what it does, see the [Manual](Manual.md); for building and testing, [Development.md](Development.md); for what's next, [Plan.md](Plan.md).

## Core abstraction: the pipeline

Every view is a serializable **pipeline**: `source → stages → render`.

```yaml
source:
  cluster: garden-dev/shoot--foo--bar   # context or Gardener path
  resource: pods                        # GVR, alias-resolved
  namespace: kube-system                # or "*"
  labelSelector: app=etcd
  fieldSelector: status.phase!=Running
stages:
  - filter: 'o.status.containerStatuses.exists(c, c.restartCount > 3)'  # CEL
  - grep: 'oom'                                                          # text match on rendered row
  - hideHealthy: true
  - sort: [-restarts, name]
  - groupBy: spec.nodeName              # planned
  - aggregate: {count: true}            # planned
render:
  columns:
    - {name: NAME,     path: metadata.name}
    - {name: NODE,     path: spec.nodeName}
    - {name: RESTARTS, expr: 'o.status.containerStatuses.map(c, c.restartCount).sum()'}
    - {name: MEM,      path: ..., type: bytes}     # human-readable
    - {name: CPU,      path: ..., type: cpu-gauge} # gradient badge, planned
  diff: {mode: highlight, ignore: [default-noise]}
```

Many features fall out of it:
- **Jumps** (`⌘J`, events) = a new source plus filters, so the filter bar shows why a pane holds what it holds.
- **Back/forward** = a stack of pipelines per pane.
- **Splits** = N pipelines sharing sources.
- Planned: **saved views / aliases** = stored pipelines (+ parameters); **shell export/import** = pipeline ⇄ `kubectl … | jq … | sort` (best effort, lossy where CEL has no shell equivalent); a **structured pipeline editor**; **AI help** that emits pipelines (safe, inspectable) rather than arbitrary commands.

Expression languages: CEL (cel-go) for filters and columns; gojq as an optional escape hatch.

## Decisions

### Language: Go

client-go/informers, `k8s.io/kubectl` packages (apply, diff, printers, exec, port-forward), cel-go, gojq, Gardener API types. Rust/kube-rs would mean rebuilding much of kubectl.

### UI framework: Wails v3 (Go backend + system webview)

- v3 over v2: multi-window (tear-off splits), improved bindings/events. Adopted in its betas; stable since 3.0.0.
- Platforms: macOS first; Linux via WebKitGTK accepted as good enough for now; Windows (WebView2) maybe later.
- Why: off-the-shelf components cover most features (see the frontend stack below); CSS variables for theming and per-context colors; Vite hot-reload; small binary via the system webview.
- Rejected: **Gio** — best raw throughput (no bridge), but terminal emulator, code editor, diff viewer and markdown would all be hand-built; pre-1.0 API. **Fyne** — retained-mode widgets are hard to make dense and fast for large live tables.
- **Bridge rule (architecture constraint):** Go owns all pipeline state (informers, stages, diff, history). The frontend is a thin view: it requests a visible row range, Go pushes batched cell deltas for that range (throttled, ≤ 10 Hz). Never ship full objects or full tables over the bridge; full YAML only on an explicit detail view.
- Keyboard-first discipline: dense layout, no gratuitous animation, own all shortcuts (suppress conflicting webview defaults).
- Escape hatch: the rendering layer is the only frontend-coupled part; any frontend component can be swapped without touching the Go core.

### Frontend: React 19 + React Compiler (TypeScript, Vite)

- Criteria: fastest + best-looking; boilerplate irrelevant (AI-written code). With the bridge rule, framework render speed is not the bottleneck — grid rendering is.
- Why React: the only ecosystem with a top-tier canvas grid and the polished-UI component stack; highest AI-generation accuracy (Svelte 5 runes vs. Svelte 4 confusion, Solid written like React) — matters since the frontend won't be hand-reviewed by a framework expert.
- Rejected: **Svelte 5** — fine-grained reactivity for free, but fewer first-class adapters (dockview, shadcn port lags) and weaker AI accuracy. **Solid** — best reactivity model on paper, smallest ecosystem.

| Layer | Choice |
|---|---|
| Main live table | Glide Data Grid (canvas) — cell deltas from bridge events applied via `updateCells`, bypassing React re-render. The last stable release (6.0.3) declares React ≤18 peers and upstream looks stalled; used with a peer override behind the pure `layout()` adapter so it can be swapped |
| Components / styling | shadcn/ui + Radix + Tailwind (themes via CSS variables) |
| Command palette (planned) | cmdk — not used for `⌘O`: it forces Enter onto the highlighted item, which breaks free-text submit |
| Splits / tabs | dockview |
| YAML view / edit / diff | Monaco (incl. diff editor), trimmed to a lazily loaded viewer; a small Monarch tokenizer for decoded JSON instead of Monaco's JSON language service and its worker |
| Terminal (exec, debug, node shell, local terminal, logs) | xterm.js |
| Motion | Motion (formerly Framer Motion), subtle only |

- Canvas constraint: no arbitrary HTML in table cells — typed columns (bytes, diff highlight, "changed, not visible" marker) are Glide custom cell renderers.
- **Status colors (`grid/tones.ts`):** a cell's tone (`ok`/`warn`/`bad`) from its column name and text, in the frontend, per column (a value counts only where the column means a state; typed columns never, except metric percentages: number columns named `%…`, `warn` from 70, `bad` from 90), built-in rules only. Not in Go: the cells are already there, so frames don't grow, goldens don't change, and time travel's recorded cells color the same. Not via the health rules either: they judge an object, the tone a cell. `layout()` picks the text color: deleted rows stay deleted; `warn`/`bad` win over the added/changed text color while the diff keeps the background; `ok` only on unmarked cells, so a mark stays visible on a cell that just turned healthy. The `ok` token defaults to `var(--color-fg)` (uncolored); a theme may set it.
- Non-table React state (panels, dialogs) lives in an external store (zustand) subscribed per component; high-frequency data never goes through React state.

### User config: `~/.kubewing/`

Plain YAML, hand-editable, git-friendly (can be versioned or dotfile-synced). kubewing reads `config.yaml`, `keybindings.yaml`, `refs.yaml` and `themes/`; it writes its own `history.yaml`, `columns.yaml` and `clusters.yaml` (into the state directory, by default the same). The exceptions are `config.yaml` and `keybindings.yaml` saved from the settings editor (`⌘,`, `⌥⌘,`): written atomically (temp file + rename) through a symlink, keeping the file's mode; Go accepts only these two names (`config.Editable`). The keybindings reference, starter and command/key/context checks are built in the frontend (`keys/keysReference.ts`), which owns the keymap; Go only reads, writes and parses the file, keeping incomplete entries in `Effective.Keybindings` so the frontend's problems keep their entry numbers. Native menu items can nest (`MenuItem.Items`: a submenu), which the app menu's Settings uses.

The settings reference is `internal/config/reference.yaml`, embedded: a valid `config.yaml` with every setting, its default (or an example) and a comment. It's not written into the user's file as comments; a file that exists is the user's, and a reference merged into it would go stale with every release. It's shown beside the editor instead. Only a new file starts from it, every line commented out (`config.Starter`), so `⌘/` brings back a setting exactly as documented. Tests keep it honest: it must load without problems and contain every JSON field of `config.Config` (walked by reflection), so a new setting can't be forgotten. The live check (`CheckConfig`) runs the same `load` as startup over the unsaved text (the other files read from disk) and returns `config.yaml`'s problems only. Saving is `WriteFile` + `ReloadConfig`, so it applies like `⌘⇧,`; a file with problems is still saved, as a hand edit would be. Planned: `views/*.yaml` (saved pipelines), `aliases.yaml`, `favorites.yaml` (bookmarked clusters).

**Font.** No font is bundled: the default is `theme.css`'s `--font-mono` stack (SF Mono, Menlo). Go validates `font` (the family can't break out of a CSS value, the size is bounded) and reports a family none of whose fonts is installed: on macOS it asks CoreText (`font_darwin.go`: the available family names, else a font's full or PostScript name), which is what WebKit's `font-family` matches, user fonts included; elsewhere it can't tell and reports nothing. It runs in `Load` (startup, reload, save), not in `load`, so the settings editor's live check (`CheckConfig`) doesn't look fonts up on every keystroke; the editor lists what a save brings beyond the live problems (`SaveConfig`'s errors of the file), and the banner hides while the editor is open. The check can't live in the frontend: WebKit's canvas doesn't see fonts in `~/Library/Fonts` (measuring there calls them missing), only the DOM does. `store/font.ts` puts the configured families in front of the default stack and sets `--font-mono`, `--kw-font-size` and `--kw-ligatures` for the DOM (`text-small`/`text-tiny` are 1-2px below the base size). The renderers that can't read CSS take `font()` whenever the config generation (`themeGen`) changes: the Glide grid (font, row/header heights from the size), xterm (`options.fontFamily/fontSize`, then a refit, since the host doesn't resize; its DOM renderer takes ligatures from the page CSS) and Monaco (`updateOptions` + `remeasureFonts`, `fontLigatures`). Zoom (`⌘+`/`⌘-`/`⌘0`, `view.zoom*`) is a px offset `font.ts` keeps in memory on top of `font.size`, so a reload keeps it relative to the new size; the shown size is clamped to Go's 8 … 24 bounds and a step starts from the shown size (one step back from a bound always shows). It changes `font()` and the CSS variables like a reload and bumps `themeGen`, so every renderer follows by the same path; the keys used to be suppressed webview defaults (the webview's own page zoom would scale the layout, not the font), now they're bindings, global and allowed from the editor (`focusMoves`). Canvas text ignores `font-variant-ligatures` and WebKit has no other switch, so with ligatures off the grid draws a zero-width non-joiner between adjacent ASCII symbols (`unligate`); monospace ligatures keep their characters' widths, so hit-testing and text selection measure the plain text.

## Watches and the source layer

- **One watch per source:** `as=Table;g=meta.k8s.io;v=v1;includeObject=Object`. Default columns come from the server's Table output, so kubectl's columns and CRDs' `additionalPrinterColumns` are free, and cells and objects always share a resourceVersion.
- **List progress:** the initial list (and a relist) is paginated, 500 per page. After each page with more to come where the API server says how many remain (`remainingItemCount`: unfiltered lists only), the list sends a `Progress` event (`source.Loaded`: objects so far, their estimated total); the objects still come as one `Relist` at the end. Some aggregated API servers' Table convertors drop the count (Gardener's copy only `continue`), while their metadata lists, served by the generic apiserver code, keep it: when an unfiltered Table page has more to come but no count, one `limit=1` `PartialObjectMetadataList` request counts the objects (`Cluster.count`), once per list, and that total serves the following pages. The registry keeps the last progress until that relist or an error and replays it to late subscribers. The view shows it in its `Status` only while not synced, so a relist's progress after the watch expired doesn't show.
- **Shared registry** keyed by (cluster, resolved GVR, namespace, selectors), ref-counted; a watch stops when the last view on it closes. Keys use the *resolved* resource, so `no`, `node` and `nodes` share one. Short-lived consumers (the node-shell dialog's node list) hold a watch and release it 30 s after they close.
- `managedFields` stripped via transform funcs; metadata-only lists, watches and gets where sufficient (the jump menu, label completion, the catalog's CRD and namespace watches).
- **Cluster catalog:** per-context discovery snapshot (resource types incl. short names, group, scope; namespaces), fetched only for contexts with an open pane — never triggers exec-plugin logins in the background. Refreshed by metadata-only CRD/namespace watches, on resolve misses and every 5 minutes. Partial discovery and forbidden namespace lists degrade to a hint.
- **Reconnect:** each context's connection has a dialer of its own (`rest.Config.Dial`), so client-go builds a transport for it rather than sharing one from its TLS/exec-plugin cache. A reconnect drops the connection (`ClusterOpener.Reconnect`, under every name it was reached by), restarts the context's shared watches in place (`Registry.Restart`: subscribers, objects and history stay; the new list reaches them as a relist; the old watch's fanout stops delivering) and restarts the catalog's watches. Sessions, port-forwards and log streams keep the old transport until they end. "Disconnected" is derived, not tracked: a synced view with a source error (cleared by the next successful list).
- **Kubeconfigs from other terminals:** a launch that hands over to a running kubewing passes the `$KUBECONFIG` path encrypted with `instance.key`. Such a cluster is addressed as `@n/<context>` (`internal/source/kubeconfig.go`); kubewing's own kubeconfig uses plain context names. The references live as long as the process.
- **Kubeconfigs in memory:** a `@n` reference is either a list of files (read anew each time, as kubectl does) or a kubeconfig built in memory under a key (`RegisterConfig`: the same key gets the same `@n`, its config replaced). The clusters dialog (`⌘⇧O`) registers Gardener targets that way, so everything downstream (the opener's connection cache, reconnect, the catalog, splits and `⌘T` staying on `@n`) works unchanged. Nothing is written to disk; a reconnect reuses the registered config (a rotated CA needs a new pick).

## Listings (`all`)

Everything in a namespace (resource `all`, `source.AllResources`) is one pane over every namespaced type, listed once rather than watched: one watch per type would be 100–200 per namespace on CRD-heavy clusters, for a view mostly used to look around.

- **A source like any other.** The registry resolves `all` itself (`Resolved.Kind` `*`, a namespace required, no selectors) and runs a snapshot (`internal/source/snapshot.go`) in place of the opener's watch: the types from discovery (refreshed, so new CRDs count; tapes: their kinds), namespaced ones only, events left out, each group/kind once; metadata-only lists, ≤ 8 at a time, ≤ 60 s for all; merged into one `Relist`, then idle. So sharing between splits, history recording and the keyed diff work unchanged.
- **Its own table.** The snapshot sends server-style column definitions and cells (`SnapshotColumns`): KIND, NAME, OWNER, FINALIZERS as cells, AGE and DELETING as dates re-derived from the timestamps (`stampColumns["*"]`), so they tick. A kind served by two groups is shown qualified. Metadata lists say `PartialObjectMetadata`: the type's apiVersion and kind are stamped on, which is what the rows' actions resolve their type from.
- **Refresh = restart.** `⌘R` (`Service.Refresh` → `Subscription.Restart`) starts the shared source anew, as a reconnect does: the new relist reaches every split, which diffs it against the last (added, removed, changed marks; a version when recording). Progress and the outcome travel as `Listed` events (`source.Listing`: types, done, when, skipped types), replayed to late subscribers like the last error and shown by the view's `Status`; the skipped list itself is fetched on request (`Service.Skipped`).
- **Rows of many types.** Actions don't use the pane's type: `row()` resolves a snapshot row's own (`rowType`: `ResolveKind` from its stamped apiVersion/kind, then the opener's `Resolve` for the GVR) and reads the whole object (`Actor.Get`). Full objects are kept per pane for the rows opened lately (`fullCache`, ≤ 64), read by the view through `view.Options.Full` for the detail's YAML and decoding; the detail polls `Object`, which re-reads it, so an open YAML follows the object. Relations read the full object too (references are in the spec). The versions (diff, field history) stay the listed metadata: the history records what the source delivered. A delete or an edit from the pane lists again (`refreshAfter`), since nothing watches.

## Clusters dialog and Gardener

- **gardenctl compatibility without gardenctl:** `internal/gardener` reads `gardenctl-v2.yaml` (identity, alias, kubeconfig, context, patterns, access-level defaults) and matches patterns as gardenctl does (Go regexps, unanchored, named groups `project`/`namespace`/`shoot`/`seed`, first matching pattern per garden). gardenctl's resolver, kubeconfig generator and session logic are under its `internal/`, and its module pulls in gardener/gardener, so the needed parts are reimplemented (~400 lines) against unstructured objects. No Gardener Go types.
- **Matching never connects:** `MatchTarget` runs on every keystroke and is pure; only `OpenCluster` (an explicit pick) connects, through kubewing's own connection to the garden (`Lookup`: `GetObject`/`ListObjects` on the `ClusterOpener`, status errors kept so NotFound is still recognized), so lookups and garden panes share one login. Where gardenctl errors on a value several gardens match, kubewing lists one target per garden.
- **Shoot kubeconfig:** gardenctl's: per advertised address (external first) a cluster with the CA from `<shoot>.ca-cluster`, the cluster extension `client.authentication.k8s.io/exec` = `{shootRef, gardenClusterIdentity}` (client-go hands it to the plugin as `spec.cluster.config`, hence `ProvideClusterInfo`), user exec `kubectl-gardenlogin get-client-certificate [--access-level]`. The first context is named `<garden>/<technicalID>` (safety rules match on it). Shoots older than Kubernetes 1.20 (the legacy flag form) aren't supported.
- **Control plane:** the seed of `spec.seedName`, in namespace `status.technicalID`: a managed seed (`garden/<seed>`) through its shoot's gardenlogin kubeconfig (access level from `kubeconfigAccessLevelDefaults.seeds`), else the `garden/<seed>.login` (or `.oidc`) secret's kubeconfig as is. Named `<garden>/seed--<seed>`, so all control planes on one seed share a connection.
- **Seed targets:** `Target{Seed}` without a shoot (a pattern's `seed` group, a gardenctl session, `⌘J`) resolves the same way as a control plane's seed (`Resolver.seed`), in all namespaces; registered under the same key, so a seed and its control planes are one connection. Remembered as `config.Cluster.Seed`; a control plane's seed isn't (it's looked up anew).
- **Recent clusters:** `config.ClusterStore` (`clusters.yaml`, ≤ 100, same-cluster dedupe, not rewritten within a minute). Kubeconfig contexts are recorded by `OpenPipeline` (whatever opened the pane), Gardener targets when they're resolved: their pane's cluster is an in-memory kubeconfig that can't be reopened from files, and two control planes on one seed are one connection. gardenctl's session targets (`$TMPDIR/garden-<effective uid>/sessions/*/target.yaml`, by mtime) are merged into the list read-only.
- **One line per shoot:** Go pairs a shoot and its control plane into one entry (`ClusterEntry.Alt`) in the recent list, matches and choices. The pair sits where the most recently used plane would be. A missing other plane is made up, never used, so the dialog's plane toggle works on every shoot and shows a known rule for both. The frontend only picks `entry` or `alt`, by the toggle. Forgetting a line removes both planes.
- **Opening lists nothing:** `⌘⇧O` opens a pane with `resource: ""` (`emptySpec`), which `applySpec` and the pane's mount never send to Go, and `⌘O` over it. `OpenCluster` tracks the catalog right away (an explicit pick may connect), so `⌘O` completes before anything is listed. The resolved context name is the cluster's context part, so badges and frame colors are there from the start.
- **Jump menu labels:** Go builds each entry's label (`replicaset web-7d4`, `pods in shop`, `control plane of bar`) and names its leading resource type in `Relation.Type` / `ClusterJump.Type`, a prefix of the label. The menu styles that prefix like a pane header's resource name, instead of guessing where the type ends in the string. Labels without a type (`scan for owned…`, `no owner`) leave it empty.
- **Clusters in `⌘J` (`Relations.Clusters`, `bridge/clusterjumps.go`):** a Shoot (`core.gardener.cloud`), Seed or ManagedSeed (`seedmanagement.gardener.cloud`) row lists ⌘⇧O entries (`ClusterEntry`, `From: "jump"`), not pipeline targets: they're another cluster, and resolving one connects (maybe a login), so it happens on the pick only (`OpenCluster`, as the dialog's). Only on a garden of gardenctl's config, so the entries' garden is known without a lookup: a cluster `⌘⇧O` registered as `garden:<identity>`, else one whose kubeconfig's API server is a garden's (`source.Server`: kubeconfig only, no connection). The frontend shows them as a section of their own, first (the highlight starts there), and opens them as `⌘⇧O` does (`openCluster`: here, split, tab).
- **`⌥⌘O` (`OtherPlane`):** Go remembers the targets `OpenCluster` resolved, a shoot by its cluster (its kubeconfig is its own) and a control plane by its seed's cluster plus the shoot's namespace there (control planes on one seed share a connection). The pane's spec (cluster, namespace) finds the target. The other plane is resolved as a pick would be. The memory lives as long as kubewing runs, like the in-memory kubeconfigs; a cluster not opened by `⌘⇧O` or `⌘J` gets an error. A resolved control plane also notes its seed's cluster (as a seed, with that shoot). On a seed's cluster the shoot is the pane's namespace's (`gardener.ShootOfNamespace`: the technical id `shoot--<project>--<name>`), else the context's namespace's (gardenctl's), else the control plane opened there last. Clusters not resolved in this run (a terminal's gardenctl kubeconfig, a restored pane) are known by their kubeconfig (`targetOfKubeconfig`, reading only): a context named `<garden>/seed--<seed>` is that seed (kubewing's naming; checked first, as a managed seed's kubeconfig has gardenlogin for its shoot); a gardenlogin context (`source.GardenloginOf`: the cluster extension's `shootRef` and `gardenClusterIdentity`) with a `shoot--` namespace is a control plane on the seed of `shootRef`, without one the shoot `shootRef`. `⌥⌘O` is bound in the `dialog` context as well (⌘O only), since an opened cluster has ⌘O over it.
- **Pane location (`Location`, `bridge/location.go`):** the header's "where am I" for a pane's cluster and namespace, found as `⌥⌘O` and the terminal's gardenctl target find it (`opened`, else `targetOfKubeconfig`, else a garden by its API server via `gardenOf`); connects nowhere. On a seed's cluster only the pane's namespace decides (`ShootOfNamespace`: control plane, else seed), unlike `⌥⌘O`, which falls back to the control plane opened there last, since the header must show what the pane lists. The seed's kind (managed, its shoot and host seed; unmanaged) comes from `gardener.Opened.Seed`: `Resolver.seed` looks up the ManagedSeed anyway to pick the connection, so it records the answer at no extra request, and `Service.seeds` keeps it by `garden/seed`. A shoot records its `spec.seedName` and, for project `garden`, whether a ManagedSeed names it (`Opened.IsSeed`, one list of `garden`'s managed seeds; a forbidden list just leaves it unknown), in `Service.shoots` by cluster. The frontend caches locations by cluster and namespace (`store/location.ts`) and clears the cache whenever a cluster is opened or switched (`openCluster`, `⌥⌘O`) or the config reloads, as resolving may have learned more. Plane hues are theme tokens (`plane-*`), fixed and distinct from safety colors. The breadcrumb's least width is measured (`useLeastWidth`: texts at their `min-width`, badges and separators at their width, gaps; re-measured by a ResizeObserver, never while hidden), not left to the browser's `min-content`: Chromium counts a truncating flex item's full text toward it unless the item's base size is 0, so the breadcrumb couldn't shrink, and a count of letters came out short and let parts spill over what follows. It clips besides, as a safety net. Landscape and seed sit in a box of their own (shrink weight 1000) so they give way before the name. Table and object views (viewer, editor) start their headers with the same component (`PaneWhere`: labels, name, location, resource, namespace), so they never drift apart; only what follows is their own.
- **Safety rules by landscape:** `safety.Policy.For` tries each rule on the context name, then on its landscape (`safety.Landscape`: the `<garden>` of a name kubewing gives Gardener clusters, `<garden>/shoot--…` or `<garden>/seed--…`), so labels and enforcement (`Guard.Prepare`) agree. Read from kubewing's names by the policy itself; for gardenctl's context names (`shoot--p--s`, `garden--<seed>-external`), which carry none, the bridge adds it: `safety.Action.Landscape` (and `Guard.RuleIn`, `Policy.ForIn`) from `Service.landscape(cluster)`, the garden `Location` finds (`opened`, else gardenlogin's `gardenClusterIdentity`, else a garden by its API server). Every Prepare, the edit check and the clusters dialog pass it; the frontend asks for a pane's rule by cluster and context (`ClusterRule`, cached by both). `Rule.ByLandscape` says the rule matched the landscape (or the garden's own name), which `safety.label: landscape` needs: only such a rule's label replaces the landscape's name in the breadcrumb (`labelLandscape`); others keep their chip. `safety.chip: false` makes that crumb `plain`: the rule's color on its text, no border or tint; the clusters dialog shows a `byLandscape` rule's label plain too (`usePlainLabel`).

## Metrics

- **Columns, not a view.** `kubectl top` values (and `kubectl describe node`'s allocated resources) are extra available columns of Pod and Node views (`metricColumns` in `internal/view/metrics.go`), referenced by name in `columns.yaml` like server columns, never among the defaults. So sort, grep, filters, splits and jumps apply without a second table.
- **Feeds, shared.** A metric column says what it's computed from; the bridge runs ref-counted feeds for the panes that show one (`internal/bridge/metrics.go`), started when a pane's columns gain one (open, type columns change), stopped when the last pane hides them or closes; a joining pane gets the last data at once.
  - *Usage:* metrics.k8s.io can't be watched, so it's polled (15 s), one feed per source key (cluster, resource, namespace, selectors) + kind.
  - *Allocation* (node `%CPU REQ` …, their own group and key, `⇧M`: the first list of every pod is slow on big clusters, so it's opt-in apart from usage, with a loading state in the status line until the first sums): one feed per cluster holding a shared registry watch on its unfinished pods (`status.phase!=Succeeded,status.phase!=Failed`, as kubectl describe node), keeping per-node sums up to date from the events (a pod's previous resources taken out, its new ones put in), pushed at most once a second. A watch rather than a list per poll: the first list is the cost, then only changes. A pod's resources are component-helpers' `PodRequests`/`PodLimits` (`source.PodResources`), the scheduler's and kubectl's rules, for the pods' percentages too. They're kept by resource name (`source.Amounts`: cpu in millicores, the rest in their unit), so ephemeral storage and extended resources are summed with no extra code, and a node's sum counts its pods (`PODS`/`%PODS` against `allocatable.pods`). Extended resources and huge pages get a `%<name> REQ` column each, only once a node of the pane has a non-zero allocatable of it (`View.extended`, collected from the nodes' events; a newly seen one re-resolves the columns, so a configured column of it appears then, and the pump re-syncs the feeds since it may be the first allocation column shown); no LIM column, as Kubernetes requires their limits to equal their requests. A configured one no node has yet is still listed in the `alloc` group (missing), so the switch hides it too. `source.Metrics` is implemented by the cluster opener (`metrics.k8s.io/v1beta1` pods/nodes, container usage summed) and by tapes (`metrics:`); NotFound/Forbidden/ServiceUnavailable are `ErrNoMetrics`, shown in the status line.
- **Outside the object.** Usage is held by the view by namespace/name (`SetMetrics`), not in the object or its hash: new data re-renders only metric cells (and the match: grep sees them), marks nothing (metric columns are `timeDerived`) and isn't recorded. The past renders them empty.
- **Their place, while off.** Hidden columns aren't in `columns.yaml`, so turning a group off (`SetTypeMetrics`) also saves its place, `metrics:` or `allocation: {after, order}`: the shown column before them and their order. Requests/limits without a place go after the usage columns. Turning on puts them back there; a missing anchor falls back to after NAME.

## Keyed diff

Object identity from watch events, not screen position (avoids viddy's row-shift, AGE-tick and same-name-recreate artifacts).

- **Identity:** rows keyed by UID → correct added/removed/changed regardless of sort; delete + recreate under the same name shows as remove + add.
- **Table diff:** per-(UID, column) rendered-cell comparison; time-derived columns (AGE, an event's LAST SEEN/FIRST SEEN) excluded. Event stamps are taken from the object by kind (`stampColumns` in `internal/view/stamps.go`), as kubectl picks them, so they tick and sort by exact time. A pod's RESTARTS (`3 (5m ago)`) keeps the server's count but swaps the "ago" for the newest `lastState.terminated.finishedAt` (`podRestarts`, type `restarts`: `3 (<RFC 3339>)`). The frontend renders it against its clock. It isn't time-derived: the timestamp moves only with a restart, so a restart is still a change, and it sorts by the count.
- **Hidden changes:** hash of the normalized object → "changed, not visible" marker.
- **Normalization / noise filter:** strip `resourceVersion`, `managedFields`, heartbeat fields (`lastHeartbeatTime`, lease `renewTime`); drop resync/relist no-ops. Path-based, user-extensible ignore rules. The rules are fixed per watch: a config reload applies to watches started afterwards, so one history never mixes two rule sets.
- **In-place stage updates:** a filter/grep change re-evaluates the match flag of the existing view instead of rebuilding it: the watch, normalized objects and diff state survive. Only a source change (label selector) re-subscribes.

## Filters

- **Grep** is one `grep:` string in the pipeline (fzf-like terms: AND, `!x`, `^x`/`x$`, `|`, quoting). Regex was considered and left out: prefix, suffix and OR cover the cases, without a second engine (RE2 vs JS) or backtracking in the log filter. Export can map it to `grep -i a | grep -vi x`. Matching runs on the lower-cased cells joined by a space; age columns match as timestamps.
- **Label selector and CEL are drafts until `⏎`.** Go dry-runs the draft against the pane's objects for the preview (`→ 298 / 340`). Label previews are exact when the draft is at least as strict as the applied selector (`view.Narrower`), else a lower bound (`≥`).
- **Label completion** counts keys and values among the source's objects matching the draft's *other* requirements (`Service.Labels`, `internal/bridge/labels.go`): from the pane's objects when the rest is at least as strict as the applied selector or the pane shows the past, else from a metadata-only list of the source; failures fall back to the pane's objects.
- **CEL completion** takes field paths from the live objects (works for every CRD without OpenAPI). The objects are schemaless, so keys that aren't identifiers complete as `["app.kubernetes.io/name"]`, not Kubernetes' `__dot__` escaping. CEL has a cost limit per evaluation; a missing field is "no match", other errors are counted and reported.

## Health rules (hide healthy)

What `hideHealthy` hides is data, not code: rules in `internal/health/health.yaml` (embedded), extended by the user's `health.yaml` (theirs first, same id replaces, `disable` drops), compiled once per config load (`health.Compile`), like the field references.

- **One rule per kind, first match.** A rule's `kinds` are globs over `group/Kind`, matched by the object's own apiVersion and kind (so the mixed-kind `all` pane works), the decision cached per kind. Terminating objects are never healthy, whatever the rule.
- **Checks, all must hold:** `builtin` (Go: pod readiness and rollout completion, which CEL would make awkward and slow), `generation` (observedGeneration ≥ generation), `conditions` (type → status, missing fails), `cel` (the filter's CEL environment; a missing field or an error fails). The common CRD shape (conditions plus observedGeneration) needs no CEL.
- **Go says what applies, not the frontend.** The frame's `Status.Healthy` carries the pane's rule title (from the resolved group and kind; a tape takes the group from its first object), so the checkbox, its tooltip and `h`'s refusal follow the rules without a second copy of the kind list in TypeScript, and follow a config reload.
- **Reload in place.** `ReloadConfig` hands the new rules to every open view (`View.SetHealth`): matches are recomputed, objects and diff state kept, like a stage change.

## History buffer

In-memory, newest snapshot + reverse field-path deltas, per shared watch (`internal/history`, diffs from `internal/fieldpath`).

- **Storage:** the newest normalized object per UID, plus one delta per older version. A delta is a list of field-path changes carrying both old and new values, so it applies in reverse: version n−1 = undo(delta n, version n). Going back is a walk from the newest object; dropping the oldest version drops its delta, with no keyframes to rebase. The same changes drive "what changed" in the diff header.
- **Lists matched by key** (containers by `name`, conditions by `type`), not by index.
- **Opt-in:** off by default ("record changes" per source). A recording watch handles ~200k events/s (normalize + hash + diff, ~5 µs/event) vs. ~1M/s without. Off, each view keeps only the previous version. Switching on takes the current objects as first versions; switching off drops the history.
- **Where:** in the shared watch (`source.Registry`), not in each view. Splits on one source share one history (and its on/off), and the object is normalized once per event, not once per split.
- **Limit:** one global memory budget (`history.budget`, default 512Mi, counting the newest copies and the changes as JSON sizes), so every object reaches back equally far — which a table-at-a-moment needs and a per-object version cap doesn't give. Past it, the oldest changes go first across all objects (down to 90%, so eviction doesn't run per event). An object's oldest kept version stays as its baseline. There's no time window: it would only cut history the budget still has room for. Versions are numbered per object, so stepping stays stable while updates arrive.
- **Tombstones:** a deleted object keeps its history until the view drops its tombstone; a recreate under the same name is another UID, so another history.
- **Lifecycle:** dropped when the last view on the source closes.
- **Time travel cost:** a step rebuilds the table from the history, ~50 ms for 10k objects with 10 versions each; quick presses merge into one step. Server cells are recorded with each version. Ages count from the moment shown (`nowOf` in `frontend/src/grid/rowcache.ts`).
- **Later:** pinning objects/views against eviction; on-disk persistence (e.g. SQLite/Pebble), blocked on secrets landing on disk in plaintext — needs encryption or exclusion first.

## Field references

Which fields name another object (`secretName`, `roleRef`, a shoot's `seedName`) is data, not code: rules in `internal/relations/refs.yaml` (embedded), extended by the user's `refs.yaml` (theirs first, same id replaces, `disable` drops). They drive the jump menu's field section (the references at a YAML view's or the editor's cursor), the marks and `⌘`-click in the viewer, and the direct references of the table's `⌘J`.

- **Path patterns, not CEL.** A rule must say *where* a reference is, so the cursor can be matched to it; CEL evaluates to values and can't. The pattern (`**.volumes[*].secret`, `subjects[kind=ServiceAccount]`, `*SecretRef`) is matched over the YAML node tree of the text shown, which has the lines and columns: one walk gives the reference, the value's position (for the mark) and the field's line span (for "everything in this volume"). The same text Go parses is what the frontend shows (the view, the diff's right side, the editor's text as typed), so nothing has to map lines between two renderings.
- **Kinds by group, not version.** Targets are `Kind`, `group/Kind` or `group/version/Kind`; a reference without a version (RBAC's `apiGroup`) resolves to the preferred one (`ResolveKind` with `group/`). Two fields naming one object are one entry (counted), compared by group/kind/namespace/name; the namespace defaults to the object's own and is dropped once discovery says the target is cluster-scoped.
- **Direct only; derived references stay in Go.** A pod's claims → their bound volumes → attachments, a stateful set's claims by the controller's naming pattern, an ephemeral volume's claim `<pod>-<volume>` aren't one field each. `relations.References` keeps them; the rules add what it doesn't list, and on a duplicate the derived entry wins (it knows more: a checked UID, "deleted" vs. "missing"). Planned on top: reverse references (the rules read backwards, e.g. the pods using a secret) and configurable chains of rule ids (see Plan).
- **Every target is looked up** (metadata only, so secrets aren't read): not there is **missing** (a field may name what was never created, unlike an owner, which is "deleted"); a failed lookup (forbidden) keeps the jump with "not checked".

## Blame

Who set each line of an object's YAML (`b`, `⌘B` in the editor), as kubectl-blame does, from `metadata.managedFields`.

- **The text shown, walked with each manager's set.** `internal/blame` (pure) parses the text the viewer or the editor shows and walks its YAML nodes together with every manager's `fieldsV1` tree (`f:` fields, `k:{…}` list items by their keys, `v:` set items by value, `i:` by index). A field starting on a line is that line's: a scalar where it's in a manager's set, a map or list only where a manager owns it as a whole (`.`, or a list item with no children listed). So the lines are the text's own, as for the field references: the editor's text as typed is blamed as it is, nothing maps lines between two renderings. Owners are ordered newest first (`time`); the gutter shows the first.
- **managedFields read on request.** The sources strip them (noise for the diff, the history and the YAML), so `Actor.GetManaged` reads the object with them. They're kept per pane and row (`blameCache`, ≤ 16) for the row's resourceVersion (5 s for a row without one): the editor asks on every pause in typing, the viewer as the object changes, and only a new version reads again. The YAML shown stays without them.
- **The gutter is Monaco's line numbers.** A `lineNumbers` function renders each line's label (escaped: Monaco inserts it as HTML) with `lineNumbersMinChars` sized to the longest (≤ 30 characters), so it's read-only and scrolls, folds and wraps with the lines for free; a class (`kw-blame`) dims and left-aligns it. The hover contribution isn't bundled, so a line's owners are the label's native tooltip. Text that doesn't parse blanks the labels at the same width (the old ones would sit on the wrong lines).
- **Now, not then.** A pane showing the past blames the object as it is now: the history keeps what the watch delivered, without managedFields.
- **Tapes:** watch items are stripped like the cluster sources'; `GetManaged` returns the tape's managedFields, and a patch adds its fields to a `kubewing` Update entry, as an API server records an edit's field manager.

## Decoding

`internal/decode` is pure. A request sends the levels (field paths resolved by Go on the first, chains after), and Go decodes from the object again each time: nothing decoded is kept. The value comes from the object at the line's field path (`fieldpath.AtLine`), not from the YAML text.

- Detection: base64 is kept only when it decodes to text, gzip or brotli text (so "admin123" stays a word); a Secret's `data` and a ConfigMap's `binaryData` always decode. gzip by magic bytes. Brotli has no magic bytes: bytes that aren't text are tried and kept only if they decompress to text; a `.br` key takes any result. Decompression capped at 16 MiB.
- The decoded diff decodes the field in both versions with the same chain.
- Out of scope: etcd/auger (protobuf as stored in etcd; kubewing only sees the API server's objects).

### Encoding (editing decoded values)

Editing a decoded value (`⌘E` in the editor) is text editing inside the edit session: the levels are encoded back into the object's YAML before the usual check, preview and merge patch, so the safety model doesn't change.

- **Stateless, from the text as typed.** `view.EditDecode` decodes a field of the editor's text (the object's YAML, or a level's decoded YAML/JSON, one document of it), not of the stored object. `view.EditEncode` takes a level back: the original value is read from the text above as it was when the level opened (`EditLevel.above`), encoded, and set into the text above as it is now. Go keeps nothing; the frontend holds each level's texts (`EditState.levels`).
- **`decode.Edit` / `decode.Encode`.** Edit gives the bytes the chain leads to, not the decode view's rendering (PEM as text; JWT and binary refused; one-line JSON indented, marked `Compact`). Encode undoes each step in the original's variant (base64 alphabet, padding, wrap width, trailing newline; gzip/brotli at best compression) and checks the round trip. Text still as decoded returns the original value, since compressing again would give other bytes for nothing.
- **`fieldpath.Replace`** sets a string at a path in YAML/JSON text by replacing only the value's characters: the scalar's span is found from yaml.v3's node position and its style (quoted, plain and its continuation lines, block scalar to its last content line). A multi-line value becomes a literal block at the old block's indentation or the collection's + 2; JSON gets a JSON string. Comments, formatting and key order stay, so the preview diff is the value alone.
- **The editor stack.** All levels' editors stay mounted, only the top one shown, so the editor above keeps its cursor and undo history. The encoded text reaches it through `Editor`'s `value` prop, applied as one undoable edit over the lines that differ (`changedRange`).

## Logs

`internal/logs` is the pure tailer; `internal/bridge/logs.go` wires it to a watch and the `kw:logs` batch events; `source.Actor.Logs` (and a tape fake) behind it. A tail has one or more sources, each a pods watch with what picks pods from it (the pane's stages for a whole-pane tail, the owner UID for a workload, names for marked pods). A marked tail has one source for all marked pods (the pane's watch) and one per marked workload/node/namespace (its pods child). Each source keeps its picked set; their union by pod UID is fed to the tailer as a relist (once every source has listed, so no pod is ended as missing meanwhile). A pane per pod is one tail per pod: the same scope narrowed by `LogsOptions.Only` (every source keeps just that pod), the pods listed by `LogsTargets.Pods`. The headless WebSocket server closes the log tails a connection started when it goes away, as it closes its panes (a tail holds a pods watch). One follower per pod container, `logs.maxStreams` concurrent, restart-resume via the RFC 3339 timestamp. The frontend renders into a read-only xterm from a bounded ring (`frontend/src/logs/`).

## Port-forward to services

A pod forward is client-go's SPDY/WebSocket port-forward (`source.Cluster.PortForward`). A service forward (`bridge/svcforward.go`) resolves to a pod forward in the bridge, as `kubectl port-forward svc/…` does, with kubectl's own helpers so the choices match it:

- **The pod:** the service's selector is a pods watch on the shared registry (`v1/Pod` resolved by kind, so tapes resolve too); its first list ranked by `podutils.ActivePods`, the most active taken. It must be running.
- **The ports:** the dialog sends service ports; `util.LookupContainerPortNumberByServicePort` maps each to the pod's target port (named target ports through the pod's containers, headless services unchanged). UDP-only service ports are refused up front.
- **No failover:** the forward is pinned to that pod, as with kubectl; it ends with the pod. `PortForwardInfo` keeps the service name and, per port, the service port next to the pod's, so the service's dialog lists its own forwards (not those to its pods directly) and offers the service ports not yet taken.

## Local terminals

`⌃T` / `⌃⇧T` start the user's login shell on the Mac (`source.RunShell`: `$SHELL -l` in a PTY via `creack/pty`, in `$HOME`) as one more session of the bridge's `startSession`, so output, input, resize, find and the pane's lifecycle are exec's.

- **A kubeconfig of its own** (`source.ShellKubeconfig`), not `--context` flags or `kubectl config use-context`: tools other than kubectl (helm, stern, k9s, scripts) read `$KUBECONFIG` too, and switching the user's current context would move every other terminal. For a kubeconfig of files, the shell's `$KUBECONFIG` is an overlay file (current context, the context with the pane's namespace) followed by those files: kubectl merges the files and the first file setting a value wins, so the overlay decides the current context and namespace while clusters, users and exec plugins come from the original files untouched (no credentials copied, a refreshed token file still read). `kubectl config set-context`/`use-context` write into the first file, the overlay. An in-memory kubeconfig (a Gardener target, `RegisterConfig`) has no files, so it's written whole. The file is `0600` in a fresh `0700` temp directory, removed when the shell ends.
- **A gardenctl session of its own** (`bridge.gardenctlSession`, `gardener.NewSession`): every shell gets a fresh `$GCTL_SESSION_ID` (`kubewing-<random>`), replacing an inherited one: gardenctl keys its target by that id (else `TERM_SESSION_ID`, which is dropped), so an inherited id would let `gardenctl target` in the shell move the launching terminal's target. On a Gardener cluster kubewing writes `$TMPDIR/garden-<effective uid>/sessions/<id>/target.yaml` as `gardenctl target` does (garden identity, project, shoot, `controlPlane`, seed), so `provider-env`, `ssh` and `kubectl-env` work without targeting. The target is found as `⌥⌘O` finds it (`opened`, else `targetOfKubeconfig`), a garden also by its API server (`gardenOf`), its project from the pane's namespace; on a seed, a `shoot--<project>--<name>` namespace (the pane's, else the gardenlogin context's) is that shoot's control plane. The session directory is removed when the shell ends; gardenctl's kubeconfigs in it go with it. Headless runs read recent targets from `-garden`'s `sessions/` and use a separate private root with a `sessions/` directory (`Gardener.ShellSessions`) for local terminals.
- **The pane's spec, not its rows:** the cluster and namespace of the focused pane (`PrepareTerminal(cluster, namespace)`), so it works from any pane kind; the namespace `""` (all) leaves the context's own.
- **A safety action** (`terminal`): the shell holds the context's credentials and nothing it runs passes the safety model, so read-only contexts refuse it and `confirm: [terminal]` asks. Same two-phase token as the other actions.
- **Environment:** kubewing's own, with `TERM=xterm-256color`, `TERM_PROGRAM=kubewing` (the launching terminal's `TERM_*`/`ITERM_*` dropped: the shell runs in xterm.js) and a UTF-8 `LANG` if none is set (a Dock launch has none).
- **Closing** cancels the session: `SIGHUP` to the shell, as a closed terminal window sends, `SIGKILL` 2 s later (`exec.Cmd.WaitDelay`). Once the shell has exited, the PTY is closed after its last output (≤ 200 ms), so a background job still holding the terminal doesn't keep the session open.
- **Keys:** bound in table, detail, logs and ended contexts only: in a running shell `⌃T` is the shell's (`terminalReserved` keeps every non-`⌘` chord there).
- Tapes fake it with the echo shell (`local:<context>$`, after a line naming the context and namespace, and one with the gardenctl target if there is one).

## Safety model

Rules are decided in Go (`internal/safety`); the frontend only shows what Go decided. Every mutation is two-phase: Go checks the rule and issues a single-use token, valid for 60 s and bound to that exact action and object (kind, context, resource, namespace, name, UID); the mutating call only runs when it redeems that token. So no path (keys, menu, context menu, palette) gets around a rule, and a confirmation can't act on another object than the one it showed. A config reload drops outstanding tokens. Deletes carry a UID precondition; edits a resourceVersion precondition; label and annotate a merge patch of only the given keys (`null` removes one) with `metadata.uid` in it, which the server refuses for a recreated object (uid is immutable). Scale patches the `scale` subresource's `spec.replicas` (autoscaling/v1, the same for every workload kind), so it needs no knowledge of the kind's schema; the row menu offers it where the object has `spec.replicas`. Rollout restart is kubectl's: a merge patch of `spec.template.metadata.annotations["kubectl.kubernetes.io/restartedAt"]` (with `metadata.uid`), for apps/v1 deployments (unpaused), stateful sets and daemon sets only (Go decides, `RowInfo.restart` says why not). Like delete it's in every rule's `confirm`, whatever the config lists: it has no dialog of its own, and replaces every pod.

**Actions on many rows.** Marked rows live in Go, in the view (`view.Mark`: toggle, a range from the anchor key to an index, all, clear), keyed like the rows. The frontend holds only the visible window of keys, so `⌘A` or `⇧End` couldn't be resolved there. Frames carry a `marked` flag per row and a count in the status. Every frame prunes marks of rows no longer shown (filtered out, tombstones), so nothing can act on an unseen row; a new source is a new view, so no marks. `PrepareMarked` reads the marks itself (never a key list from the caller), resolves each row as `Prepare` does, skips rows the action doesn't fit (scale: no replicas; restart: not a restartable workload; debug: not a pod), and calls `Guard.PrepareBatch`. That checks the rule once (all or nothing: a refusal withdraws the tokens already issued) and issues **one token per object**, under one decision: one `needsConfirm`, one summary, and for strict rules or deletes of more than 20 objects the count to type instead of a name. Execution is the single-object calls, each redeeming its own token (≤ 8 in parallel, from the frontend), so UID preconditions, per-object binding and the 60 s expiry are unchanged, and partial failures are reported per object.

## Frontend

- **Single command dispatcher:** every shortcut (JS keydown or native menu accelerator) resolves to the same command id and goes through one dispatcher. The native menu is built from the live keymap (`keys/appMenu.ts`); every item shows its key in the native shortcut column, but only global `⌘` chords are working key equivalents. Scoped and plain keys are `displayOnly`: AppKit has no display-only key equivalent, so Go (`internal/app/menukeys_darwin.go`) disables those items while their menu is closed and enables them while it's open, so a menu shortcut never fires inside a text field.
- **Modal editor:** the YAML editor (edit, node-shell YAML) only lets its own keys reach the app; global keys and menu commands wait until it's closed.
- **Generated lists with completeness tests:** the row menu comes from `actions/registry.ts` (a test fails for any `object.*` command without an entry); the cheat sheet from `keys/cheatsheet.ts` (a test fails for any command no section mentions).
- **Swappable bridge transport:** Wails IPC in the app, WebSocket to a headless Go backend in tests and browser dev.
- **Layout:** the store's split tree is the source of truth; `store/dock.ts` converts to and from dockview's layout. Keyboard resizing (`layout.resize`) changes the split sizes in the tree, and the dock pushes them like any other change: the divider is the pane's top/left one along that axis (the innermost split where it isn't the first child), else its bottom/right one, so a middle pane stays anchored at its top. Step and minimum are pixels (40, and dockview's own 100px group minimum, so the tree never asks for less than dockview shows), turned into shares of the measured tab; a nested split's minimum honors its children's shares.
- **Focus follows mouse** (`focusFollowsMouse`): `mousemove` on a pane, not `mouseenter`, and only with real movement (`movementX/Y`) and no button held. A layout change under a resting pointer (a split opening, a pane closing) fires enter events and zero-movement moves, which would otherwise take the focus from the pane just opened. `S.hoverFocus` takes it only from another pane's own context (table, terminal, logs, YAML view or editor), never from a field, an overlay, the tab switcher or a maximized pane. The left element is blurred as a click would, since the store moving focus doesn't blur Monaco.
- **Copy on select** (`terminal.copyOnSelect`): `term/copyOnSelect.ts`, shared by the shell `Terminal` and `LogView`, copies the xterm selection through the bridge (`copyText`: Wails' clipboard, the page's in the browser build) when the left button that started on the pane is released (`mouseup` on the window, as a drag may end outside it; a `setTimeout` lets xterm finish the selection first). Not on xterm's `onSelectionChange`: it fires at every step of a drag and when find selects a match, which would overwrite the clipboard while searching. The setting is read on each release, so a reload applies to open panes without remounting them.

## Windows

Panes can live in windows of their own (Wails v3's multiple windows). Each window is its own page with its own store: nothing is shared between them, and a pane moves by being handed over.

- **Routing (`bridge/windows.go`):** Go's events used to go to every window. Now every stream (a table pane's frames, a shell's output, a log tail's lines) has an owner window, set when it's created: bound methods that start one take a `context.Context`, in which Wails names the calling window (the WebSocket transport passes its connection's `?window=` the same way, so in the browser each connection is a window). Its events go to that window only; config, columns and port-forwards still go to all. Each window has an ordered queue drained by its own goroutine: Wails delivers on the main thread, so the router never delivers while holding its lock (a window closing runs a hook on that thread that needs it).
- **Handoff (`store/transfer.ts`):** `Reassign` switches the owner of the pane's streams under the router's lock and returns, per session, the sequence number of the last chunk the old window was sent (session and log events are numbered). The old window waits until it has received up to that number (a call's reply and the window's events travel separately), snapshots the pane's state, the shell's transcript, the log backlog and the time-travel timeline, and sends them to the target window as a window message. The target prepends the snapshot to whatever arrived after the switch, so no chunk is lost or doubled even while the shell prints. It inserts the pane where it was dropped (`S.insertPane`, like `movePane`; ids are per window, so the pane gets a new one), and calls `Resync` so the next frame is complete. A shell's exit that arrives before its pane is held until the pane does. The store's orphan subscriber skips handed-off ids, so leaving the old store doesn't close them in Go. A split object view borrowing its table's server pane opens its own in the new window (frames can't go to two windows).
- **Opening and closing:** a new window is reserved under a name (`w1`, …) and gets events only once its frontend calls `WindowReady` (queued meanwhile); `OpenWindow` returns then, and headless the page opens it itself (`window.open` + `AwaitWindow`). A detached window starts with no tabs and renders nothing until its pane arrives; its last pane leaving or closing closes it (`detached` in the state; the main window still gets a fresh pane). A window closing (red button, or its connection dropping) closes the streams it still owns, the same rule the headless server always applied per connection.
- **Cross-window drag:** WKWebView's `screenX/Y` don't match Wails' window frames, and the page can't know which window is in front, so during a drag the app asks Go (`Pointer`): AppKit's `NSEvent.mouseLocation` and `windowNumberAtPoint` give the mouse and the frontmost window under it (another app's counts as outside), and `convertPointFromScreen` the point in that window's content view, which is its page (the title bar is hidden). One question is in flight at a time; a pointer inside the page is answered without asking. Outside every kubewing window, a drop opens a window (`OpenWindow` at the drop point, as big as the pane plus a tab bar, offset by where the grip was grabbed) and hands the pane to it as a new tab. Over another window the source sends it `dragover` with the point in its page; that window resolves the target with its own DOM (the same `targetAt`, tab dwell included), draws the preview and answers `dragtarget`. On release the source sends `dragdrop` and hands the pane over to the target in that window's final answer (waiting up to a second for it, so a quick release doesn't race the last answer). The browser build has no native windows: `Pointer` fails and the drag falls back to the page's screen coordinates and the windows' frames (`Windows`).
- **Tabs:** a tab's header drags across windows the same way (`components/windowDrag.ts` holds the pointer tracking and the `dragover`/`dragtarget`/`dragdrop`/`dragleave` exchange both drags share; `dragover` says `what` is dragged). A window a tab is dragged over answers with a place in its tab bar (`tabTargetAt`: the tab-reorder `dropIndex` over the bar, else last) instead of a pane target, and doesn't switch tabs on dwell. The handoff (`sendTab`, message `handofftab`) moves all the tab's panes in one `Reassign`, the snapshot per pane as for a single one; `S.insertTab` renumbers the panes (ids are per window) and remaps a split object view's `from`. A split object view whose table moves with it keeps sharing the table's server pane; one left behind, or moved without its table, opens its own.
- **Front window:** menu clicks (`kw:command`) and launch handoffs (`kw:launch`) go to the window most recently focused (`WindowFocus`), not to all of them.

## Process model

- **Single instance per config directory:** Wails' single-instance lock (in `NSTemporaryDirectory()`), keyed by the config directory, checked before `application.New` (which would exit silently); the second launch says so on stderr and hands over its kubeconfig path.
- **Login environment** (`app.LoginEnv`, first thing in `main`): a launchd start (parent pid 1, not the `Detach` child) has launchd's minimal environment, yet client-go runs exec credential plugins with kubewing's `PATH`. It runs `$SHELL -i -l -c 'command env -0'` once (stdin `/dev/null`, 10 s timeout) and adopts the result, minus `PWD`/`OLDPWD`/`SHLVL`/`_`. The output is cut between unique markers because profiles print things (banners, iTerm's escape codes). This is what VS Code does. Running the shell per plugin call instead would cost a profile load each time. On failure the launchd environment stays and the log says so. Not in `-headless` (tests keep the environment they were given).
- **Detaching:** launched from a terminal, kubewing re-runs itself in a session of its own (stdin `/dev/null`, output appended to `kubewing.log`, rotated at 10 MiB). Piped/redirected output and `-headless` never detach.

## Releases

- **The tag is the version.** No file in the repository holds it, so a release needs no "bump" commit. The only commit a release makes is a final's stamped changelog. `make` derives it with `git describe` and stamps it in at build time: `-ldflags -X internal/app.Version` (the `-version` flag and the About box, which Wails builds from the app's `Description`, not from `Info.plist`) and `plutil` on the bundle's copy of `Info.plist`. `CFBundleShortVersionString` takes numbers only, so a candidate's `-rc.N` lives in `CFBundleVersion` alone.
- **Tagged locally, published by the push.** The script decides the next version and checks the commit (on `main`, clean, equal to `origin/main`, tests pass), but never pushes: the person releasing keeps that step. The workflow only reacts to the pushed tag and re-checks that it's annotated and on `main`. The release notes travel in the tag's message, so the workflow needs nothing but the tag, and GitHub's own generated notes aren't used. `actions/checkout` fetches tags as lightweight copies, so the workflow re-fetches the tag to read its message.
- **Notes from `Changelog.md`.** Commit subjects are written for developers and miss what a change means to users, so the notes are kept by hand in a [Keep a Changelog](https://keepachangelog.com)-style file, filled as features land rather than reconstructed at release time. `scripts/release.sh` copies the `[Unreleased]` section into the tag (`--cleanup=whitespace`, as `strip` would drop the `###` headings as comments). A final stamps the section with its version and date in a `release: vX.Y.Z` commit, which the tag points at, so the file in the tagged tree says which version it is; candidates don't stamp, so their notes accumulate until the final. The file is also the source of the updater's "what's new" (see Updates), by way of the releases' bodies.
- **Candidates:** `vX.Y.Z-rc.N` → a GitHub pre-release, never "latest". The updater offers them only with `update.prereleases`.
- **Unsigned by Apple:** no paid developer account, so no Developer ID and no notarization. The linker ad-hoc signs only the arm64 binary; `make dist` re-signs the whole bundle ad hoc (`codesign --deep -s -`), since a bundle whose seal doesn't cover `Info.plist` and its resources is reported as "damaged" after download, which users can't get past as easily as Gatekeeper's "unverified developer". The zip is made by `ditto`, which keeps the bundle's metadata and signature intact. A download carries the quarantine flag, so the first launch needs "Open Anyway"; files a program downloads itself (not a browser) don't get it, so the updater doesn't hit this again.
- **arm64 only, zip only:** Wails needs cgo against Cocoa/WebKit, so the build runs on a macOS runner, not cross-compiled. Asset names are stable (`kubewing-<version>-macos-arm64.zip`) for the updater to find. macOS runners cost more on private repos, so CI runs on release tags only.
- **Minimum macOS 13:** Go's runtime needs it, so the Makefile builds the cgo parts for it too (`MACOS_MIN`, as `-mmacosx-version-min` in `CGO_CFLAGS`/`CGO_LDFLAGS`; wails' own flags would say 10.13, and our Objective-C would target the build machine's SDK, so a newer macOS API there would go unnoticed), and `LSMinimumSystemVersion` in `Info.plist` says the same.
- Actions are pinned by commit SHA, the job alone gets `contents: write`, and releases are made with the runner's `gh` rather than a third-party action.

## Updates

`internal/update`, held by `app.App` (not `bridge.Service`: it's about the app, not clusters), pushes its `Status` as `kw:update` on every change.

- **One request, not the API:** the updater downloads `releases.json` from `github.com/dguendisch/kubewing/releases/latest/download/`. It's GitHub's release list (`/repos/…/releases?per_page=50`) cut to what the updater reads: every release's tag, body (the notes), pre-release flag and assets, with GitHub's `sha256:` digest per asset. The API itself allows 60 anonymous requests an hour **per IP**, and behind a company proxy or VPN everyone shares a few egress IPs, so other tools used it up long before kubewing's daily check. Release downloads aren't rate-limited. The `release-list` workflow publishes the file: release.yml calls it after publishing, and it runs again when a release is edited or deleted on GitHub (the notes are the "what's new"), or by hand. It takes the list from the API with the runner's token, drops drafts (the token sees them), and uploads it to the latest release, replacing the old copy. "Latest" is never a pre-release, so the list there names the candidates too. When the latest release has no list (404: releases from before this, or a re-upload in progress), the updater falls back to the API, as it used to. Any other failure of the download is reported as it is, not hidden behind the fallback. The list adds no trust: the zip's signature is what's checked (see Release signing).
- **What's offered** (`Pick`, pure): the newest release above the running version that has the zip (one still uploading has none). Finals only, candidates with `update.prereleases`. The notes are the target's and every final's in between, newest first. A candidate's body accumulates its final's changes so far (see `make release`), so earlier candidates add nothing. Versions compare with `x/mod/semver`. Only `X.Y.Z` and `X.Y.Z-rc.N` are releases. Development builds (`0.0.0-dev`, `-N-gsha`, `-dirty`) are never offered anything, since whoever built them knows better.
- **Schedule:** `update.checkDays` (default 1, `0` = off, at most 365), applied on start and on every config reload. `Run` compares the last check's wall-clock time with now every hour instead of sleeping for the interval: Go's timers stop while the Mac sleeps, so a 24 h timer would run late by however long the lid was closed. A clock set back (last check in the future) checks at once. A failed check doesn't count as one, so the next tick retries. `update.json` in the state directory keeps the last check and the skipped version. A manual check works with automatic checks off and on development builds.
- **Release signing:** GitHub's digest only shows the download arrived intact. It's served from the same place as the zip, so whoever can replace the zip can replace the digest too. The release workflow signs each zip with an ed25519 key (the `KUBEWING_SIGNING_KEY` secret) as `<zip>.sig`. The public half, `build/release-key.pub`, goes into the binary (`-ldflags -X update.PublicKey`). The signature covers `kubewing-release-v1`, the asset's name and its sha256. The name holds the version, so an older signed zip can't pose as a newer release. A build without the key checks but never installs. Releases before the updater are unsigned and are offered as "download…" only.
- **Install** (`Installer`), every step before the swap undoable:
  1. Download into a staging folder beside the bundle (the same volume, so the swap is a rename), hashing as it streams.
  2. Compare with GitHub's digest, verify the signature.
  3. Unpack with `ditto -x -k`, which keeps the bundle's metadata.
  4. Check the new bundle with `codesign --verify --deep --strict`, and that its binary runs `-version` and reports the offered version.
  5. Swap the two bundles with `renamex_np(RENAME_SWAP)`, one atomic step, so there's never a moment without an app. The old bundle, now in staging, is removed with it.
  6. Start a detached `sh` that waits (at most a minute) for this pid to exit, then `open`s the bundle, and quit through Wails, so its shutdown ends sessions and port-forwards. The pid and path are passed as arguments, never written into the script.
  
  The swap replaces the whole directory, so the new binary is a new vnode, and the kernel's per-vnode signature cache (see `make app`) doesn't kill it. Files a program downloads aren't quarantined, so Gatekeeper doesn't ask again. In-place install is refused under App Translocation (the app was never moved out of where it was downloaded, and macOS runs it from a read-only random path), when the folder isn't writable, without a bundle (`make build`, `go run`) and without a release key. The dialog then offers the release page.
- **Release notes as Markdown:** rendered from `marked`'s tokens straight into React elements (`update/Markdown.tsx`), never as an HTML string, so no sanitizer is needed. Raw HTML shows as text, and images become links (nothing remote is loaded). `marked` was already in the bundle (glide-data-grid's), whose 4.x lexer is enough. Links resolve against the repository at the note's tag (`Manual.md#x` → `blob/v0.3.0/Manual.md#x`), only `http(s)` stays a link, and a click goes through Go's `OpenURL` to the default browser. Navigating the webview would replace the app's page.
- **Fake releases:** `-releases <file>` reads GitHub's JSON from a file (`update.File`) and `-releases-current` sets the version to compare against. In the app (`make try-update`) the installer is `update.Simulated`, which walks through the phases with a fake download and then fails, and there's no state directory, so a try doesn't change the real skip or last check. The `Updater` takes any `AppInstaller` for this. Headless has no schedule and no installer, so e2e tests check on request and get "download…".

## Testing strategy: assert on state, not pixels

UI regressions are caught by checking the app's state as data at every layer. Full-app screenshot diffs are not used.

- **Go core: view-model goldens (most tests).** Scenario tapes (starting objects + scripted watch events: add/update/delete/relist/recreate under the same name) run through `pipeline → bridge output` against a fake cluster; cell deltas, row keys and diff markers are compared to golden files. Property tests (`rapid`) for the keyed diff: re-sorting produces no "changed" markers, AGE ticks never count, recreate shows as remove + add, a no-op relist produces no deltas. The bridge rule is tested too: nothing outside the requested row range, no full objects unless asked for, ≤ 10 Hz under event storms.
- **Bridge contract.** Generated TS bindings are committed (a CI check is planned).
- **Frontend logic without a browser.** Keymap resolution and command effects are plain unit tests; a static check catches binding collisions per context and confirms suppressed webview defaults stay suppressed. Glide cell renderers are split into a pure `layout(cell, theme)` (unit-tested) and a thin `draw()`. Layout operations keep the tree valid and focus always on an existing pane.
- **E2E on meaning.** Playwright drives the frontend in Chromium against the headless Go backend replaying tapes; tests read state through `window.__kw.inspect()` and use ARIA snapshots for DOM parts.
- **Introspection hook:** test builds expose `window.__kw.inspect()` (layout tree, focus, per-pane pipeline, visible rows/cells, selection, open overlays), and `__kw.config` (the config store) for a test to turn on a setting the shared `testdata/config` leaves off.
- **Guardrails against AI-made regressions.** Goldens are the spec: updating them takes an explicit `-update` flag and the change is reviewed as its own diff. Lint bans raw colors outside theme tokens.
- Planned: a WKWebView smoke suite for what Chromium can't reach (native menu accelerators, IME); invariant fuzzing with random key sequences; a golden-guard hook on `testdata/`.

Example — "a shortcut opens an overlay", by layer:

| Layer | Assertion |
|---|---|
| Keymap unit | `resolve("Meta+Shift+O", {focus: "table"})` → the command, also from a split, the YAML view and a terminal (xterm.js and Monaco must not swallow it) |
| Command unit | the command on a store state → overlay open, input focused, previous focus remembered for `Esc` |
| E2E (Chromium) | press the key → `inspect().overlays` contains it; ARIA snapshot shows a focused combobox; `Esc` → focus back on the same pane and row |
| Smoke (WKWebView) | the key triggers no native dialog and isn't consumed by the menu bar |
